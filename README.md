# Свой сервер для Claude без VPN — методичка

Основа — курс [«Claude без VPN и с нулевым риском блокировки: свой сервер за вечер»](https://platform.anticourses.com/share/z7soc8ioah/p/07-04_claude-bez-vpn-svoy-server-232).
Этот документ — та же схема, но дополненная реальными граблями, на которые напоролись
при эксплуатации именно такой связки (VPS + Claude Code + CloudCLI) в бою, не один вечер,
а месяцами.

## В чём идея

Вместо VPN до claude.ai — свой сервер в Европе с Claude Code на борту и веб-панелью
(CloudCLI) поверх него. Заходишь на свой домен по HTTPS с любого устройства, VPN не нужен.

## Пять терминов

- **Сервер (VPS)** — арендованный виртуальный компьютер, работает 24/7.
- **Терминал** — текстовый интерфейс для команд.
- **SSH** — защищённый удалённый доступ к серверу из терминала.
- **Домен** — человекочитаемое имя сервера (`example.com`) вместо IP-адреса.
- **HTTPS** — шифрованное соединение с сайтом/панелью, требует сертификат.

## Сколько это реально стоит

Из курса:
- Зарубежная карта/PayPal: от ~200 ₽/мес (Webdock Essential, €2.15).
- Российская карта: ~1840 ₽/мес (Timeweb с бэкапами).
- Домен: ~200 ₽ в первый год.

**Поправка по опыту:** эти минимальные тарифы (обычно 1-2 ГБ RAM) хватает **только** под
голый Claude Code + CloudCLI и ничего больше. Как только на сервер добавляется что-то
ещё — свой бот, локальная модель (Ollama), несколько Docker-контейнеров — 1-2 ГБ становится
тесно очень быстро. На практике конфигурация "2 vCPU / 2 ГБ" ощутимо не хватало уже при
паре параллельных фоновых процессов; после апгрейда до "4 vCPU / 8 ГБ" стало комфортно.
Если планируется когда-нибудь развивать сервер дальше панели — сразу берите тариф с
запасом (от 4 ГБ RAM), докупать проще один раз, чем потом мигрировать данные.

## План на вечер

### Шаг 1. Купи сервер

Сгенерировать SSH-ключ и передать его на новом сервере при создании:

```bash
# Mac/Linux
ssh-keygen -t ed25519 -C "moy-server"
cat ~/.ssh/id_ed25519.pub | pbcopy   # скопировать публичный ключ
```

```powershell
# Windows (PowerShell)
Get-Content ~/.ssh/id_ed25519.pub | Set-Clipboard
```

Два варианта хостинга (из курса):
- **Webdock** — для зарубежных карт/PayPal.
- **Timeweb** — для российских карт.

**Дополнение:** при выборе провайдера проверьте, есть ли у него встроенные снапшоты
диска — это отдельная и куда более быстрая линия защиты, чем восстановление из бэкапа
скриптом, если что-то пойдёт не так во время экспериментов с сервером.

### Шаг 2. Купи домен и направь его на сервер

Домен покупается отдельно, DNS A-запись указывает на IP сервера. Распространение DNS
может занять от нескольких минут до пары часов — не паникуйте, если домен не открывается
сразу после настройки, просто подождите.

### Шаг 3. Зайди на сервер по SSH

```bash
# Timeweb (обычно root)
ssh root@185.xx.xx.xx

# Webdock (обычно отдельный пользователь)
ssh alex@185.xx.xx.xx
```

**Дополнение — сразу после первого входа, до всего остального:**

SSH почти на любом публичном IP получает постоянный фон брутфорс-попыток входа с первого
дня — это не паранойя, а норма для интернета. Прежде чем ставить что-либо ещё:

1. Поставьте `fail2ban` (банит IP после N неудачных попыток входа).
2. Настройте `ufw` (или другой firewall) — открыт только 22 (SSH), 80/443 (веб), и
   при необходимости порт CloudCLI-панели.
3. Рассмотрите отключение входа по паролю (только по ключу) — если планируете входить
   только по SSH-ключу, это закрывает целый класс брутфорс-атак одним действием.

**Реально обнаруженная и неочевидная проблема с firewall'ом:** после **перезагрузки**
сервера `ufw` иногда не полностью применяет свои правила обратно в ядро — конфиг
(`/etc/ufw/user.rules`) на диске остаётся полным, а фактически загруженная цепочка
(`iptables -L ufw-user-input -n --line-numbers`) может содержать меньше правил, чем
должна. Внешне выглядит так: `ufw status` показывает, что порт разрешён, локально
сервис слушает порт нормально, а снаружи — не достучаться. Разово чинится командой
`ufw reload`, но чтобы не ловить это заново после каждой перезагрузки, добавьте systemd
юнит, который прогоняет `ufw reload` один раз при каждом старте:

```ini
# /etc/systemd/system/ufw-full-reload.service
[Unit]
Description=Full ufw reload after boot (workaround for incomplete rule load)
After=ufw.service network-online.target
Wants=network-online.target

[Service]
Type=oneshot
ExecStart=/usr/sbin/ufw reload

[Install]
WantedBy=multi-user.target
```

```bash
systemctl daemon-reload
systemctl enable --now ufw-full-reload.service
```

Если после будущей перезагрузки какой-то порт вдруг "пропал" снаружи, хотя всё выглядит
настроенным правильно — сначала сравните число правил в конфиге и в реально загруженной
цепочке, а не сразу грешите на хостера.

### Шаг 4. Поставь Claude Code и залогинься

```bash
curl -fsSL https://claude.ai/install.sh | bash
claude --version
```

Если при первом запуске `claude` ловите 403/сетевую ошибку — почти всегда дело в IPv6:

```bash
echo 'precedence ::ffff:0:0/96  100' | sudo tee -a /etc/gai.conf
```

```bash
claude              # первый запуск, логин через браузер
claude --continue   # вернуться к прерванной сессии
```

### Шаг 5. Панель CloudCLI и HTTPS

Дальше — установка Node.js, CloudCLI, настройка Caddy (реверс-прокси + автоматический
HTTPS-сертификат) и firewall под панель. Это тот шаг, где реально удобно делегировать
рутину самому Claude Code: дать ему одним запросом задачу "установи Node.js, разверни
CloudCLI, настрой Caddy на моём домене с HTTPS, открой нужный порт в файрволе, проверь,
что всё работает" — и он сам пройдёт по всем пунктам, спрашивая подтверждение на
рискованные шаги.

**Дополнения по безопасности, которых в курсе нет:**

- CloudCLI-панель обычно ставится и работает **от имени root** — это стандартная схема
  для одиночного личного сервера, но значит, что любая уязвимость в самой панели или в
  случайно опубликованном порте — это сразу root-доступ ко всему серверу. На личном
  сервере с одним пользователем это приемлемый компромисс, но держите панель **только**
  за HTTPS с паролем/2FA, никогда не публикуйте её порт "для теста" без прокси.
- Если Claude Code настроен с обходом запросов на подтверждение действий
  (permission bypass) — это ускоряет рутинные задачи, но означает, что модель может
  выполнить деструктивную команду без паузы на "ты уверен?". Держите это включённым
  только в связке с регулярными бэкапами, а не как "экономия одного клика".
- Панель по умолчанию логирует происходящее — если через неё же гоняются секреты
  (токены API, пароли ботов) в аргументах команд или логах, они могут случайно
  засветиться во встроенном просмотрщике логов панели. Не храните секреты в
  переменных командной строки, которые видно через `ps aux`/логи.

## Что у тебя теперь есть

- Доступ к Claude из браузера с любого устройства без VPN, по своему домену.
- Файлы и история диалогов — на своём сервере, а не только в облаке.
- Готовая площадка для дальнейших проектов: тот же сервер потом легко расширяется
  под свои сервисы (боты, небольшие веб-приложения и т.п.) — см. раздел ниже про то,
  как это делать, не превращая сервер в кашу.

## Проблемы, с которыми реально столкнулись (и как их избежать)

Этот раздел — то, ради чего документ дополнен относительно оригинального курса.

**1. Ресурсы кончаются внезапно, когда сервер "уже не просто под Claude".**
Стоит добавить на тот же сервер что-то ещё, требовательное к CPU/RAM (свой бот,
локальная LLM через Ollama, несколько Docker-контейнеров) — и однажды команды в Claude
Code начинают выполняться заметно дольше обычного, вплоть до нескольких десятков секунд
там, где раньше уходили секунды. Первым делом в такой ситуации проверяйте `uptime`
(load average) и `free -h` (свободная память), а не грешите сразу на сеть или сам
Claude. Отдельно: если сами параллельно гоняете несколько фоновых тестовых процессов —
не забывайте их останавливать, накопленные "хвосты" от старых запусков — частая причина
именно такой деградации, а не что-то более экзотическое.

**2. Firewall "теряет" правила после перезагрузки** — см. Шаг 3 выше. Симптом почти
всегда один и тот же: снаружи сервис недоступен, локально всё выглядит нормально.

**3. Новые сервисы стоит с самого начала заворачивать в Docker, а не ставить на голый
хост.** Так проще: (а) не ловить конфликты версий Node/Python между разными проектами
на одной машине, (б) чисто сносить/переносить сервис без остатков в системных путях,
(в) явно видеть, что вообще крутится на сервере, одной командой `docker ps`, вместо
разбора `systemctl list-units` вперемешку с ручными процессами.

**4. Секреты в аргументах командной строки видны всем, у кого есть доступ к серверу.**
Если сервис получает пароль/токен через `ExecStart=... --password xxx` в systemd-юните,
он полностью виден через `ps aux` и в логах панели. Передавайте секреты через переменные
окружения из отдельного файла (`.env`, `EnvironmentFile=` в systemd) с ограниченными
правами доступа (`chmod 600`), а не прямой строкой в команде запуска.

**5. Бэкапы нужны ДО того, как они понадобятся, а не после.** Личный сервер с рабочими
проектами на нём стоит бэкапить не только у хостера (снапшоты), но и отдельным скриптом
с выгрузкой куда-то ещё (например, в облачное хранилище) — так, чтобы падение самого
хостинг-провайдера не означало потерю всего разом.

## Частые вопросы

**Сколько это стоит в итоге?**
От ~200 ₽/мес (зарубежная карта, Webdock) или ~1840 ₽/мес (российская карта, Timeweb
с бэкапами) + ~200 ₽ за домен в первый год.

**А это законно?**
Аренда сервера в Европе и заход на собственный сайт по HTTPS — обычная практика,
ничем не отличается от хостинга любого личного проекта.

**А Anthropic не заблокирует мой аккаунт?**
Честный ответ, без прикрас: доступ к Claude через собственный стабильный европейский
IP-адрес формально ближе к "обычному использованию", чем через шэйred VPN-IP с тысячами
других пользователей (у которых чаще случаются автоматические ограничения "подозрительная
активность"). Это снижает вероятность проблем, но не даёт официальной гарантии — такой
способ подключения не документирован и не одобрен Anthropic явно, вы действуете на свой
риск. Если аккаунт для вас критичен — не подключайте одновременно с нескольких
IP/устройств одной сессией, не автоматизируйте агрессивные параллельные запросы, и
следите за официальными условиями использования Anthropic на случай их изменения.

**Claude Code на сервере тратит мой лимит Pro?**
Да, подписка одна на все режимы: чат, панель на сервере — всё из одного лимита.

**Сервер нужно обслуживать?**
Минимально — обновления раз в месяц можно попросить сделать сам Claude Code прямо в
диалоге. Плюс проверяйте раз в какое-то время `free -h`/`df -h`, чтобы не упереться
в нехватку памяти или диска незаметно.

**Можно посадить на один сервер команду?**
Схема личная: одна подписка Claude, один владелец панели. Общий доступ нескольким
людям к одному аккаунту/панели — вне сценария, под который это всё спроектировано.

**Что будет, если сервер упадёт?**
Восстановление из бэкапа хостинг-провайдера (снапшот) — самый быстрый путь. Отдельно
держите свою копию важных данных за пределами одного провайдера (см. пункт 5 в разделе
про грабли выше).

**У меня уже есть подписка, но нет опыта с терминалом. Точно получится?**
Да, схема рассчитана на пошаговое выполнение без специальной подготовки — но заложите
себе больше времени, чем "один вечер", если что-то из терминологии выше в новинку.

**Могу я работать и с компьютера тоже?**
Да, панель открывается в браузере с любого устройства. Отдельно возможен вариант с
Claude Desktop.
